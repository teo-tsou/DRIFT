Cross-Cluster Migration

Wire edge clusters together so VMs and pods can live-migrate between them

Wire the cross-cluster mesh

Select the clusters that should live-migrate between each other. Wiring builds a full mesh — every selected cluster peers with every other (EVPN stretched-L2 for VM IP continuity + routes to all peer pod-CIDRs + CA-trust union + decentralized-migration gate). It's idempotent: add a cluster later and re-wire with the full set. Kubeconfigs and the node-agent token are already in place from provisioning.

MEC API

Trigger an ETSI MEC-021 Application Mobility relocation — the follow-me flow

Step 1 — Application Mobility Services

A registration is long-lived: it declares an application for mobility and, for the UE it names, opens the pQoS subscription that lets degradation events drive relocation on their own. Procedures in step 2 are fired against a registration. Deregister what you are no longer demoing — every extra AMS turns each pQoS event into another procedure.

Edge applications
Set what each app needs on its row — max latency (ms), min downlink (Mbps), blank = platform default — then Register. Those numbers arm that app’s own pQoS subscriptions, so a degradation moves only the apps it actually breaks.
—
Registered (AMS)
Register as many as you like — each one is monitored. The radio only picks which registration step 2 reuses, so it does not mint a new AMS each time.
—
Step 2 — Trigger a mobility procedure

Fires a mobility procedure against a registration. Pick one above to reuse it; with none selected this registers a fresh AMS first, which is fine for a one-off but leaves a registration behind. Optimal Edge Selection picks the target, or honours the one you pin.

Pod name (pod kind) or VirtualMachine name (vm kind).
Result

No procedure triggered yet. Fill the form and hit Trigger Migration — decision and cutover status appear here live.
